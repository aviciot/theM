## Problem

The current run event delivery uses Redis Pub/Sub (`PUBLISH` / `SUBSCRIBE`).
This is at-most-once: a client that disconnects and reconnects misses every event
published during the gap. The `runstream.Stream` reconnect logic re-subscribes to
the channel but cannot recover messages already published. For long-running LLM
orchestrations this means a reconnecting browser sees a blank or partial stream
with no recovery path.

---

## Design decisions (corrections to first draft)

### 1. Continuous cursor — no gap at replay-to-live transition

The naive approach of

    XRANGE key {last_id+1} +          ← replay
    XREAD BLOCK 0 STREAMS key $       ← live from "newest"

has a race: any entry written between the end of XRANGE and the moment XREAD
starts listening at `$` is silently dropped.

**Correct approach:** after XRANGE replay, record the last stream entry ID
actually processed. Transition to `XREAD BLOCK` from *that* ID, not from `$`.

    XRANGE key {last_id+1} +          ← replay; note last returned ID L
    XREAD BLOCK 0 STREAMS key L       ← live from L; no gap possible

On a fresh connection with no prior `last_event_id`, read from `0-0` on the first
XRANGE (gets all history up to MAXLEN), then continue from the last entry seen.

The cursor is a single variable that starts at the client-supplied `last_event_id`
(or `0-0`) and advances with every entry processed, whether from replay or from
live blocking reads.

### 2. Run transport metadata — no 2-second fallback, no key-existence check

**Correction (supersedes draft section 2):** Do not use `if stream_key_exists →
use Streams, else → use Pub/Sub`, and do not use a 2-second fallback timeout.

A valid LLM orchestration may take 30+ seconds before its first token. A 2-second
key-existence check would incorrectly lock the connection to Pub/Sub for the
entire run lifetime.

**Correct approach:** store `events_transport` as a column on `them.runs`.
Values: `'pubsub'` (legacy/default) or `'streams'` (Phase 11c runs). The Go
handler reads this value once when a run is created and uses it for the entire
connection lifetime.

DB change (Phase 11c-A migration `db/025_events_transport.sql`):

```sql
ALTER TABLE them.runs
  ADD COLUMN IF NOT EXISTS events_transport TEXT NOT NULL DEFAULT 'pubsub';

ALTER TABLE them.runs
  ADD CONSTRAINT runs_events_transport_check
  CHECK (events_transport IN ('pubsub', 'streams'));
```

The Go bridge sets `events_transport = 'streams'` when creating a new run row,
IF `RUN_EVENTS_MODE` is `dual` or `streams`. For `pubsub` mode it leaves the
default `'pubsub'`.

Expected behavior by mode:
- `RUN_EVENTS_MODE=pubsub`: all runs get `events_transport='pubsub'`, Pub/Sub only
- `RUN_EVENTS_MODE=dual`: new runs get `events_transport='streams'`, Streams + PUBLISH; legacy rows keep `'pubsub'`
- `RUN_EVENTS_MODE=streams`: new runs get `events_transport='streams'`, Streams only, no PUBLISH

This eliminates the race window: by the time any Go handler starts reading events,
the `events_transport` value is already decided and stable.

### 3. Atomic dual publish (Lua script) — with TTL management

During Phase 11c-A, XADD, PUBLISH, and TTL management must be a single atomic
operation. Multiple separate calls have observable failure windows.

**Correct approach:** a Redis Lua script that performs all operations atomically
in a single round-trip. Lua executes atomically on the Redis server.

```lua
-- atomicPublish(stream_key, channel, maxlen, safety_ttl, final_ttl, is_terminal, payload, dual_publish)
-- Returns the stream entry ID generated by XADD.
local stream_key   = KEYS[1]
local channel      = KEYS[2]
local maxlen       = tonumber(ARGV[1])
local safety_ttl   = tonumber(ARGV[2])
local final_ttl    = tonumber(ARGV[3])
local is_terminal  = ARGV[4] == "1"
local payload      = ARGV[5]
local dual_publish = ARGV[6] == "1"

-- 1. XADD with MAXLEN approximate trim
local entry_id = redis.call('XADD', stream_key, 'MAXLEN', '~', maxlen, '*', 'data', payload)

-- 2. PUBLISH on legacy channel if dual-publish is enabled
if dual_publish then
  redis.call('PUBLISH', channel, payload)
end

-- 3. Set retention TTL atomically
if is_terminal then
  redis.call('EXPIRE', stream_key, final_ttl)
else
  if redis.call('XLEN', stream_key) == 1 then
    redis.call('EXPIRE', stream_key, safety_ttl)
  end
end

return entry_id
```

**The Stream is the durable source of truth.** PUBLISH is a real-time delivery
optimisation that may be removed in Phase 11c-D.

### 4. Redis TTL for stream lifetime — fully inside the Lua script, not split

**Correction (supersedes draft section 4):** TTL management must be entirely
inside the Lua script. The previous draft split TTL responsibility between the Lua
script (safety TTL) and the Go handler (final TTL). This is wrong:

- No Go client may be connected when the terminal event is published
- The client may disconnect before the terminal event arrives
- The bridge may restart between terminal event publish and the EXPIRE call

**Terminal TTL is applied by the Lua script in the Python publisher.** The Go
handler does not call EXPIRE at all.

TTL schedule (both applied inside Lua):

1. **Safety TTL (48h)**: applied inside Lua when `XLEN == 1` (first event only).
2. **Final TTL (24h)**: applied inside Lua when `is_terminal` is true.

**Centralized terminal event set:**

```python
TERMINAL_EVENT_TYPES = frozenset({'done', 'error', 'canceled', 'terminated', 'timed_out'})
```

### 5. Retention sizing — MAXLEN validation

MAXLEN ~5000 validated against real workload shapes in Phase 11c-C:

| Test | Result |
|---|---|
| 1000-token run | PASS — all events preserved |
| 5000-token run (MAXLEN boundary) | PASS (29s) |
| 6000-token run (over MAXLEN) | PASS — oldest ~1000 trimmed, ≥4900 retained |
| 800 tool-heavy mixed events | PASS (3.9s) |
| `replay_unavailable` on stale cursor | PASS (30s) |

### 6. Server-assigned event_id — monotonic cursor, no server-side duplicates

The Go handler assigns `event_id` from the stream entry ID for every event
forwarded to the client. The stream entry ID is the cursor.

**During replay (XRANGE):** entry IDs are in order; no duplicates possible.
**During live (XREAD BLOCK from last cursor L):** XREAD returns entries strictly greater than L; no duplicates.
**Replay-to-live transition:** continuous cursor produces no gap and no overlap.

Client deduplication (`Set<string>` of seen `event_id` values) remains a safety
layer against retried HTTP connections.

## Approach comparison

| Property | Pub/Sub only | Streams + dual-publish |
|---|---|---|
| Delivery guarantee | At-most-once | At-least-once with replay |
| Reconnect recovery | None (events lost) | Full replay from last_event_id |
| Python changes | None | Add Lua script call (11c-A) |
| Go changes | None | New Streamer interface + mode (11c-B) |
| Redis memory overhead | Zero | ~75KB/active run at MAXLEN 5000 |
| Rollback | N/A | Per-phase, independent |

## Stream key naming

```
them:dash:run:{runID}:stream     ← stream entries (XADD / XRANGE / XREAD)
them:dash:run:{runID}:tokens     ← pub/sub channel (legacy; removed in 11c-D)
```

Both follow the existing `them:dash:run:` namespace documented in `docs/REDIS.md`.
