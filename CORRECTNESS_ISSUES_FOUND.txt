ISSUE 1: SHUTDOWN ORDERING IS WRONG
================================================================================

Current (INCORRECT) sequence:
1. preDrainHook() → closes event sinks  ← WRONG: happens BEFORE HTTP drain
2. httpServer.Shutdown() → drains HTTP connections
3. closers.Close() → closes Redis clients

Problem:
- Event sinks close BEFORE HTTP finishes draining
- In-flight HTTP handlers can still call Emit() on closed sink
- Emit() after Close() returns error, events lost
- Second WithPreDrainHook() call REPLACES first (runCancel), breaking goroutine cleanup

Correct sequence should be:
1. preDrainHook() → runCancel (cancel background goroutines)
2. httpServer.Shutdown() → drain in-flight HTTP (wait for handlers to finish)
3. Close event sinks with deadline (after HTTP fully drained)
4. Close Redis clients

Fix Required:
- Remove WithPreDrainHook() for event sinks
- Create eventSinkCloser adapter implementing server.Closer interface
- Register event sink as closer BEFORE redisEvents in dependency order
- Event sink Close() called automatically after HTTP drain completes

Code locations:
- go/cmd/them/main.go:518-527 (remove WithPreDrainHook call)
- go/cmd/auth-server/main.go:150-163 (same issue)
- go/cmd/mcp-service/main.go:133-151 (same issue)

HTTP timeout behavior:
- If httpServer.Shutdown() times out, handlers MAY still be running
- Event sinks will close anyway
- Events from timed-out handlers will be lost
- This is acceptable (timeout means handlers are stuck/slow)

ISSUE 2: RETENTION SAFETY IS INCOMPLETE
================================================================================

Current implementation (UNSAFE):
- Checks XPENDING for pending messages
- If ANY pending exists → skip trim (conservative)
- If NO pending → trim everything older than 24h

Problem:
"No pending messages" ≠ "all messages consumed"

Scenario:
1. Consumer group exists but consumer stopped/idle
2. 1000 unread messages sit in stream (age: 48h)
3. Zero pending (nothing claimed)
4. Retention runs: XPENDING returns empty
5. Trim executes: deletes all 48h-old messages
6. Result: 1000 undelivered messages LOST

Root cause:
Code only protects PENDING, not UNREAD messages.

Fix Required:
- Check BOTH pending AND unread messages before trim
- Get last delivered ID for consumer group: XINFO GROUPS <stream>
- Only trim messages OLDER than last-delivered-id
- If no consumers in group: skip trim (unsafe to delete)

Pseudocode:
```
pendingInfo = XPENDING stream group
if pendingInfo.count > 0:
    skip trim (pending messages exist)

groupInfo = XINFO GROUPS stream
for group in groupInfo:
    if group.consumers == 0:
        skip trim (no active consumers, unread may exist)
    lastDeliveredID = group.last_delivered_id
    if lastDeliveredID == "0-0":
        skip trim (nothing delivered yet, all unread)

# Safe to trim only if:
# - No pending messages
# - All groups have active consumers
# - Messages older than ALL groups' last-delivered-id
```

Code location:
- go/cmd/event-writer/retention.go:85-120 (trimStream method)

Test case:
1. Start consumer, consume 100 events
2. Stop consumer (leave group intact)
3. Add 1000 new events (age: 48h via timestamp manipulation)
4. Wait for retention run
5. Verify: 1000 unread events NOT deleted
